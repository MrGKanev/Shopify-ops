# Преглед на документацията и оставащата работа

Дата: 21.09.2026. Обхват: всички 20 налични Markdown файла в `docs/`, включително `superpowers/`, съпоставени с текущото работно дърво, routes, views, конфигурация, CI и тестове.

## Извод

Основната Laravel миграция и голяма част от описаните продуктови подобрения вече са в кода. Документацията смесва актуални инструкции, исторически планове и непотвърдени production задачи. Старите незачеркнати стъпки **не са автоматично оставаща работа**.

Най-важното сега е:

1. Да се поправят deployment инструкциите и твърденията за действащ parity CI.
2. Да се приключат с реални доказателства SMTP, restore, TLS/proxy и UAT проверките.
3. Да се актуализира UI планът според вече използваните компоненти, вместо да се изпълнява отначало.
4. Да се проверят текущите незавършени в Git refactor промени, преди да се считат за приключени.

„Имплементирано“ тук означава намерена реализация; „има тест“ означава намерен тестов код, **не успешно изпълнение**. В тази проверка не са изпълнявани PHPUnit, Larastan, frontend build или browser/UAT тестове. Локално липсват `vendor/` и Composer в PATH. Няма достъп до доказателства за production конфигурация и проведени репетиции.

### Разлики, които не бива да се затварят механично

- **Dashboard „7-day chart“:** текущият controller взима последните 7 snapshot записа (`$recent->slice(-7)`), а не изгражда 7 календарни дни. При празни дни/няколко отчета дневно това са различни резултати. Да се уточни очакването: „последни 7 отчета“ или реално daily aggregation, после да се синхронизират UI, тест и документация.
- **Bulk-ignore:** старият план споменава включване в още пет report views. Наличието в Run Audit не затваря автоматично този по-широк обхват. Да се потвърди дали допълнителните места още са желани; да не се добавят само защото историческият план ги изброява.
- **Log search:** `q` е реализиран, но старият план споменава и date range; текущият `RunLogController` филтрира tool/status/error. Ако date-range search е изискване, то остава отделна задача.
- **Приети продуктови отклонения:** по-строгите Note Flags/Duplicate Address/Spot-check и премахнатата settings history не трябва да се възстановяват автоматично като „липсващ parity“. Нужна е нова продуктова заявка, ако решението се променя.

## Реално оставаща работа

### P1 — преди production sign-off

- [ ] Изпълнение на текущия CI/test/build набор върху точния release commit; запазване на резултатите. Историческите test counts не са заместител.
- [ ] Реален SMTP smoke test от staging с правилните secrets: rule recipient, fallback recipient, доставка и failure handling. Наличието на notification тестове не доказва deliverability.
- [ ] Backup **и restore репетиция** в изолирана среда: DB, файлове, правилен `APP_KEY`, decrypt на store credentials, права и boot. `VerifyBackupArchive` и съответните tests са полезни, но archive validation не е restore rehearsal.
- [ ] Проверка през реалния production proxy: HTTPS scheme, client IP, secure cookies, HSTS и trusted proxies. `SecurityHeadersTest` и readiness тестовете не валидират конфигурацията на външния proxy.
- [ ] Две production-like UAT/cutover репетиции или документално доказателство, че вече са проведени. Запис: дата, среда, commit, dataset, резултати, owner/sign-off. Не е необходимо повторно изтриване на legacy дървото.
- [ ] Потвърждение за реално работещи Horizon/scheduler, alerts и избран observability backend/получатели. Има health/operational код и тестове, но не доказателство за live работата им.

### P1 — документация, която може да подведе deployment

- [ ] Runbook: root paths; `pnpm install --frozen-lockfile` и `pnpm run build` според текущия lockfile; актуален release gate от `.github/workflows/ci.yml`.
- [ ] Parity/test-audit/spec/plans: ясно обозначаване като история; премахване на твърдението, че differential suite се изпълнява в текущия CI. Точният архивен commit/tag трябва да се провери, не да се измисля.
- [ ] UAT checklist: отделяне на приключилия repository cutover от непотвърдения production sign-off; актуализиране на `src/ToolRegistry.php`, `order_types.json`, `laravel/` препратките. Horizon вече е избран в приложението, не е ново нерешено архитектурно решение.

### P2 — UI и продуктови уточнения

- [ ] Актуализация на frontend плана: `button`, `card`, `stat-tile`, `data-table`, `badge`, `alert`, `empty-state`, `page-header` вече съществуват и са използвани в reports, admin, orders, customers, metafields, dashboard и layout.
- [ ] Целенасочен преглед на оставащите изгледи, вместо повторна масова миграция. Да се проверят light/dark, mobile, forms, tables и empty/error states в браузър.
- [ ] CSS usage audit преди премахване на правила. `resources/css/app.css` е 2099 реда; това само по себе си **не доказва** колко правила са неизползвани. Старите числа „350 unused“ и „30 views без dark“ не са текущо измерване.
- [ ] Изрична component reuse насока при нужда: общо правило за reuse вече има в `AGENTS.md`; конкретният guardrail от UI плана не следва да се счита автоматично изпълнен.
- [ ] Решения за calendar-day chart, bulk-ignore извън Run Audit и date filters, описани по-горе.
- [ ] Корекции в audit-checks/search-lookup: CSV възможности по инструмент и реалната fresh-read/cache политика.

### P2 — текущият refactor и неговото приключване

При започване на този преглед работното дърво вече съдържаше 24 променени Result класа, четири нови базови Result класа и пет нови wrapper теста. Те не са промени от този документационен преглед.

- [ ] Проверка на тези промени с relevant unit/feature tests, static analysis и formatter в среда с инсталирани зависимости.
- [ ] Отделно потвърждение кои duplication цели действително са затворени: извличането на DTO properties в базов клас не означава, че fetch/analyze/orchestration дублирането е премахнато. `RunScanReport` не бива да се описва като пълна унификация на всички report workflows.
- [ ] Да не се твърди пълно coverage на 24-те класа само заради петте нови теста; нужен е mapping към всички засегнати consumers и тяхното поведение.

## Какво може да се махне и какво запазих

Най-добрите кандидати за изваждане от активната документация са двата `superpowers/plans` файла, parity design и старият test audit. Те са **история, не активен backlog**. Преди физическо изтриване е добре уникалните решения да имат проверена архивна Git препратка, а входящите links да се актуализират.

Не изтрих допълнителни файлове: оперативните ръководства остават полезни, а историческите документи съдържат решения и ограничения, които още не са безопасно заместени само от текущия код. Това не означава, че са актуални инструкции.

`docs/code-duplication-review.md` вече беше маркиран като изтрит в работното дърво **преди** този преглед. Не възстановявам файла и не представям изтриването му като извършено сега. Самото му изтриване не доказва приключване на всички refactor задачи.

## Предложена организация

Да останат ясно разделени: потребителски ръководства, operational runbooks, един кратък текущ backlog и обозначена migration история. Този отчет консолидира находките към посочената дата; историческите checkboxes и числа не трябва да се ползват като текущ release status.
