# План за консистентност на интерфейса

**Дата:** 2026-09-24. **Статус:** остатъчен план; основната компонентна миграция е вече приложена.

## Текущо състояние

През този преглед са потвърдени осем споделени Blade компонента в
`resources/views/components/`:

| Компонент | Предназначение | Потвърдени употреби* |
| --- | --- | ---: |
| `<x-button>` | action бутони | 65 view файла |
| `<x-card>` | content wrappers | 22 view файла |
| `<x-stat-tile>` | dashboard/trend показатели | 2 view файла |
| `<x-data-table>` | таблици с обща обвивка и header | 58 view файла |
| `<x-badge>` | status/risk indicators | 16 view файла |
| `<x-alert>` | success, warning и error съобщения | 62 view файла |
| `<x-empty-state>` | празни резултати | 5 view файла |
| `<x-page-header>` | title, subtitle и actions | 69 view файла |

\*Броят е брой Blade файлове, които съдържат съответния component tag към тази
дата, а не брой индивидуални рендерирания.

Следователно старото твърдение, че няма компоненти и че всички view файлове
трябва да бъдат мигрирани, не е вярно. Не е необходима нова масова миграция.

`resources/css/app.css` е 2107 реда. Това само по себе си не доказва неизползван
CSS; стари оценки за конкретен брой „мъртви“ правила не са текущо измерване и не
трябва да се ползват като основание за изтриване.

## Цел

Да се уеднаквят само оставащите разминавания и да се запазят съществуващите
компоненти като първи избор за нов и променян UI, без промяна на визуалната
посока, бизнес поведението или JavaScript/Alpine логиката.

## Оставаща работа

### 1. Целенасочен UI преглед

- [ ] Прегледай в браузър представителни екрани от reports, admin, orders,
  customers, metafields, saved reports, dashboard и authentication.
- [ ] За всеки проверен екран провери light и dark theme, narrow viewport,
  filter forms, таблици с хоризонтален overflow, празни резултати и error state.
- [ ] Записвай конкретни отклонения по route/view и screenshot; не прави извод,
  че дадена директория е коректна или некоректна само по наличие на `dark:`
  класове.
- [ ] Отстранявай намерените отклонения в малки, тематични промени, след
  визуална повторна проверка на засегнатия екран.

### 2. Компонентна последователност

- [ ] При нов или съществено променян Blade UI използвай съществуващия компонент
  за button, card, data table, badge, alert, empty state, page header или stat
  tile, когато той покрива случая.
- [ ] Ако компонентът не покрива реален повтарящ се случай, първо разшири
  съществуващия му API или добави малък, добре обоснован вариант; не въвеждай
  паралелен набор от ad-hoc utility комбинации.
- [ ] Не принуждавай уникални layout-и в общ компонент. Компонентът е средство
  за повторяемите UI примитиви, не заместител на семантичния markup.
- [ ] Проверявай променените компоненти в поне една съществуваща и една нова или
  различна употреба, тъй като промяна в тях има широк визуален обхват.

### 3. CSS usage audit преди cleanup

- [ ] Направи измерим usage audit на custom правилата в `resources/css/app.css`
  спрямо Blade, JavaScript и генерираните/динамични class names.
- [ ] За всяко правило, предложено за премахване, потвърди, че не се използва от
  динамичен markup, external content или theme variant.
- [ ] Премахвай само потвърдено неизползвани правила на малки групи.
- [ ] След всяка група изпълни frontend build и прегледай засегнатите екрани в
  браузър. Размерът на bundle-а е допълнителен сигнал, не критерий за коректност.

### 4. Проверка при промени

- [ ] За Blade/component промени изпълни най-тесните приложими feature tests.
- [ ] При промяна на CSS или frontend assets изпълни `pnpm run build`.
- [ ] За UI промени направи browser проверка на засегнатия flow в light и dark
  theme; автоматичните feature tests не удостоверяват визуалното състояние.

## Извън обхвата

- Няма redesign на цветове, типография или бранд без отделна продуктова задача.
- Няма масово пренаписване на всички Blade view файлове само за да използват
  компонент.
- Няма CSS изтриване по приблизителни бройки или само защото файлът е голям.
- Няма промяна на business logic, routes или JavaScript поведение като част от
  този план.

## Критерий за приключване

Планът е приключен, когато представителните flows са визуално проверени в
поддържаните themes и viewport-и, намерените отклонения са отстранени или са
записани като отделни продуктови задачи, и всяко CSS cleanup решение е подкрепено
с usage audit, build и повторна визуална проверка.
